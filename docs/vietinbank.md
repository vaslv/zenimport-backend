# Первый банк: VietinBank iPay

Источник: открытая пользователем страница `https://ipay.vietinbank.vn/`, осмотр 6 октября 2026. Пользователь выбрал первый импорт по текущему периоду на странице: **06.09.2026–06.10.2026**. При осмотре счётчик показывал 135 строк, 14 страниц по 10. Это наблюдение, а не уже выполненный импорт. Номер счёта, имена, суммы и реальные строки в fixtures не сохранялись.

## Проверенная разметка

Английская страница `/payment-history?accountNo=…`, тип Current account. Выбранный номер дополнительно сверяется с `.vt-select__single-value .cus-option`. Таблица `table.cms-table`, колонки DATE, DESCRIPTION, AMOUNT, BALANCE; дата/время `DD/MM/YYYY HH:mm:ss`, подписанные суммы VND с запятыми группировки. Диапазон строк и общее количество — `.table-pagination-total-range` и `.table-pagination-total-total`. Номера страниц — **a[role=button]**, aria-label `Page N`; это не нативные button. Выбор периода виден в открытом Filter. Другие языки, валюты, кредитные/сберегательные счета пока отклоняются.

## Как загрузить выбранный месяц

1. Загрузить или обновить расширение `extension` в Chrome. В отдельной SPA сохранить локальный адрес `http://127.0.0.1:18791` и API_TOKEN из `.env`; ZENMONEY_TOKEN в расширение не вводить.
2. В банке открыть Current account → Transaction history. Выбрать 06.09.2026–06.10.2026, очистить необязательные текстовые/суммовые фильтры, выбрать All и применить Search. Оставить Filter открытым, чтобы период был виден.
3. Открыть страницу 1. Нажать настоящую иконку расширения и «Собрать весь выбранный период VietinBank». Держать popup открытым, не менять банковскую вкладку. Сбор переходит по номерам страниц, проверяет счёт/фильтры/счётчик, ждёт стабилизации каждой страницы. Одновременный второй сбор запрещён.
4. В preview сверить число с банковским счётчиком. Нажать «Отправить на сервер» — это отправка **в локальный backend**, не в ZenMoney.
5. В SPA проверить исходные операции и метаданные импорта. Повторный идентичный импорт не создаёт дубликаты. Никакие операции в ZenMoney на этом этапе не записываются.

После полного сбора банк остаётся на последней странице. Для повторного сбора вернуться на первую. До 2000 операций за один сбор; больший диапазон разбивать вручную. При ошибке весь сбор не отправляется. Сбор одной текущей страницы тоже доступен, но помечается частичным, если не покрывает весь счётчик. Период из полей фильтра сам по себе не доказывает, что пользователь нажал Search: это обязательный шаг пользователя. complete означает только покрытие строк текущего поиска, а не полноту всей истории счёта.

## Идентификация и ограничения

В таблице нет отдельного подтверждённого банковского transaction ID. Описания содержат разные формы reference и операции без него. Не считаем произвольный фрагмент описания надёжным ID.

Для точных повторов используется SHA-256 от номера счёта, исходной даты/времени, нормализованной суммы, остатка и описания. Метод явно помечен `reference_kind=fingerprint`, версия ключа `vib:f1`. Исходные дата/время, сумма, описание и остаток сохраняются отдельно от нормализованных date/amount_minor. Часовой сдвиг не применяется.

Если fingerprint отличается, но время и сумма совпадают с ранее принятой fingerprint-операцией, backend отклоняет импорт с 409 для ручной сверки. Это консервативное поведение может остановить две законные операции одинаковой суммы в одну секунду, зато не объединяет их молча. Полностью одинаковые строки внутри одного сбора также останавливают его. Изменение одновременно даты/суммы и остальных полей без стабильного банковского ID может не распознаться как исправление; требуется дальнейшее изучение деталей операции/экспорта. Автоматический matching и запись пока отключены в LIVE.

HTML, cookies и банковские токены не читаются и не отправляются. Debug — только явное локальное скачивание JSON полей. Реальные финансовые fixtures не попадают в Git.

## Проверка

Тестовая страница повторяет подтверждённую структуру с искусственными данными. Проверяются popup → сбор двух страниц → локальный HTTP import → повтор, fingerprint, частичная загрузка, неверная дата/валюта/разметка/счёт, изменение контекста, проверка метаданных сервером и неоднозначные повторы. Реальное управление иконкой Chrome и полный импорт 135 пользовательских строк требуют пользовательской загрузки/обновления расширения.

В headless-тесте popup открывается прямым URL без жеста Chrome toolbar, поэтому activeTab не выдаётся браузером. В **временной тестовой копии** manifest явно разрешён только синтетический `ipay.vietinbank.vn`, перехватываемый Playwright fixture. Боевой manifest не получает постоянных прав на банк и использует activeTab по настоящему клику пользователя.

## JSON истории (адаптер 2.0.0-json)

Подтверждён endpoint `https://api-ipay.vietinbank.vn/ipay/wa/getHistTransactions` и структура предоставленного пользователем ответа. Пример содержит **100 из 135** записей, `currentPage=0`, `nextPage=1`, `pageSize=100`. Страницы API и страницы таблицы — разные вещи. Полнота всего периода ещё не подтверждена. Четыре записи без `trxId`.

Новый основной путь:

1. Обновить установленное расширение в Chrome и открыть историю VietinBank.
2. Нажать «Получить JSON VietinBank», закрыть popup и выполнить обычный Search в банке **без перезагрузки вкладки**.
3. Снова открыть расширение: оно показывает счёт, диапазон строк и общее количество. Результат переживает закрытие popup и хранится только в памяти сессии Chrome. Срок приёма/восстановления — 10 минут.
4. Нажать «Отправить на сервер» для сохранения в локальную базу. Частичный ответ явно помечен частичным. Чтобы получить следующую страницу API, снова включить захват перед действием банка, которое действительно запрашивает следующую страницу. Переключение каждой страницы таблицы может не вызывать API.
5. Альтернатива: выбрать сохранённый JSON ответа (включая .txt) через поле загрузки файла. Это тот же парсер и те же проверки. Пустой/ошибочный ответ не даёт импортировать предыдущий preview.

Это одноразовое пассивное наблюдение за fetch/XHR конкретного endpoint, а не повтор банковского запроса. Расширение не читает тело запроса, cookies или заголовки. MAIN world передаёт только разрешённые поля ответа через изолированный bridge; backend token остаётся в доверенном контексте расширения. Входящие сообщения считаются недоверенными: проверяются отправитель/вкладка/срок захвата и весь payload. Сама банковская страница технически может подделать сообщение, поэтому сохраняется явный просмотр перед импортом. Автоматическое объединение страниц разных поисков не выполняется: контракт параметров запроса и завершение пагинации ещё предстоит проверить.

Верхнеуровневые `requestId`, `sessionId`, `checksum`, сообщения банка и неизвестные поля отбрасываются до сохранения. Разрешённые исходные поля каждой операции хранятся в `raw.details`: сумма, направление, дата/время, банковские ссылки, реквизиты контрагента и отделений. D → списание, C → зачисление; VND целыми числами. `processDate` имеет формат DD-MM-YYYY HH:mm:ss без конвертации часового пояса. Банковский ID хранится как `vib:id:<trxId>`; при пустом ID используется fingerprint с теми же составляющими, что у DOM-адаптера. При потенциальном пересечении DOM/JSON по времени и сумме импорт останавливается для сверки вместо тихого создания дубликата.

`capture.complete` относится только к одному ответу, покрывающему все строки результата; даты выбранного фильтра из JSON неизвестны и остаются null. Историю вне полученных страниц не считаем загруженной. Нулевой результат пока показывается ошибкой счётчиков и ничего не импортирует. Неизвестные валюты, неоднозначные суммы, некорректные даты, неполные страницы и повторяющиеся ID отклоняются.

Проверки: парсер исходного пользовательского файла в Docker без вывода финансовых значений; синтетические fetch/XHR, закрытие/reopen popup, сохранение реквизитов, отсутствие session/request/checksum в хранилище, повторный импорт, очистка захвата, загрузка файла и некорректный файл. Успешный захват живого банковского запроса требует ручного обновления расширения и нового Search пользователем.

### Если после Search остаётся «Ожидаю» (0.1.1)

Первый живой захват у пользователя не сработал; конкретная причина пока не подтверждена. Исправлен воспроизводимый сценарий XHR с сохранённым до инъекции open(): ответ теперь определяется также по responseURL. Добавлен резервный обработчик chrome.devtools.network.onRequestFinished/getContent, который не зависит от обёрток fetch/XHR банковского приложения.

После обновления расширения закрыть и заново открыть DevTools банковской вкладки (Network). Включить «Получить JSON VietinBank»: статус должен содержать «Захват через Network подключён». Закрыть popup, изменить период, нажать Search и проверить появление нового getHistTransactions; открыть расширение для preview. Без нового запроса новая история не появится. DevTools должен оставаться открытым до завершения запроса. Старые запросы, OPTIONS/HEAD, другие endpoint и ответы других вкладок не читаются; тело запрашивается только при активном захвате. Секретные поля ответа отбрасываются до передачи в service worker, данные запросов не копируются. Готовый результат по-прежнему отправляется в backend только явно.

Документация API: https://developer.chrome.com/docs/extensions/reference/api/devtools/network . Контракт обработчика DevTools проверен с имитацией API (callback/Promise/base64, очистка секретов, отказ от старых/чужих запросов). Интеграционный браузерный тест покрывает сохранённый open(). Живой DevTools-захват в пользовательском Chrome ещё требует проверки.

### Упрощённое меню

Основная кнопка теперь называется «Получить историю». Выбор «Последний месяц / Последние 6 месяцев» показывает даты для ручного выбора в банке (Вьетнам, календарные месяцы с корректировкой последнего дня). Он не меняет банковский фильтр автоматически и не доказывает полноту периода. После получения ответа — «Сохранить для проверки» в локальный backend, затем «Проверить операции» открывает раздел review. Найденные кандидаты видны и в LIVE; подтверждение/запись LIVE по-прежнему заблокированы.

Файл, сброс ожидания, выгрузка диагностики и старый DOM-метод спрятаны под «Если загрузка не работает». Для обычной загрузки выбирать между техническими способами больше не требуется. Полная шестимесячная загрузка и подтверждённые правила получателя/категории описаны как следующий этап в docs/PLAN.md; они ещё не реализованы.

### Разовое исследование параметров запроса

Для настройки автоматизации добавлена команда «Собрать схему запроса» в диагностике. Только в этом явно включённом режиме DevTools анализирует тело запроса локально; в схему сохраняются имена/типы полей и ограниченный перечень дат/параметров страницы. Значения sessionId, requestId, checksum, accountNo и токенов не сохраняются, заголовки не анализируются. Обычный сбор ответа по-прежнему не читает тело запроса. Подробный план и подтверждённый лимит банка в 30 дней: docs/vietinbank-automation.md.
