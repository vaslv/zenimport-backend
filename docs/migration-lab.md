# Репетиция смены сервера: изолированное окружение

Это явно запускаемая приёмка отдельного тестового пользователя ZenMoney.
Обычные тесты и CI используют только искусственный API. Токен, ID пользователя,
ответы API, счета, журнал отправки и файлы SQLite находятся в `.local/`,
исключённом из Git и стандартного Docker build context.

## Исходное состояние

Перед началом сохранить исправления ревью отдельными локальными коммитами в
трёх проектах. SDK 0.6.1 установлен из проверенного vendor wheel; Chrome 0.1.9;
схема backend 6. Не обновлять рабочий контейнер и установленное расширение.
`.idea/` соседнего SDK не включать в коммиты.

Тестовая идентичность закрепляется по приватному журналу прежней завершённой
приёмки SDK (`user`, `cleanup.state=verified`). Это не свободно введённый новый
ID. Тестовый токен должен отличаться от рабочего. Init читает рабочий `.env`
только для проверки различия токенов и запрета рабочего HTTP-порта; контейнеры
не монтируют этот файл и не получают рабочий токен.

В аккаунте могут быть существующие данные. Они не удаляются ради пустого
состояния. Приёмка создаёт собственные счета и сохраняет исходные сущности
для независимой проверки их неизменности. Полное копирование рабочего
аккаунта на этом этапе не требуется.

## Создание окружения

Из корня backend:

```sh
python3 scripts/migration_lab.py init \
  --root .local/migration \
  --token-file ../ZenMoneyAPI/.env \
  --identity-file ../ZenMoneyAPI/.local/live.json \
  --main-env .env
```

Команда не обращается в сеть. Создаёт новый UUID запуска, каталог с правами 700,
`identity.json` и `lab.env` с правами 600, разные API-токены серверов A/B и
отдельные каталоги SQLite `server-a/`, `server-b/`. Пароль ZenMoney не копируется:
контейнер читает `ZENMONEY_TEST_TOKEN` из указанного read-only файла. Существующий
запуск не перезаписывается. По умолчанию используются loopback-порты 18892/18893;
можно передать `--ports PORT_A PORT_B`. Не использовать занятые порты.

Подставить выведенный путь в переменную. Не выводить содержимое файла:

```sh
LAB_ENV=/absolute/path/from/init/lab.env
docker compose --env-file "$LAB_ENV" -f compose.migration-lab.yaml \
  --profile tools build tools
docker compose --env-file "$LAB_ENV" -f compose.migration-lab.yaml \
  --profile tools run --rm --no-deps tools inspect
```

Отдельный Compose не наследует production compose.yaml. Имена проекта, образа
и сети содержат UUID запуска. Профили A/B не запускаются командой tools.
Контейнеры работают без root, с read-only корнем, сброшенными capabilities,
отдельными bind-томами и без автоматического restart. Обычный образ backend
не включает live runner: используется только явный target `migration-lab`.

Inspect выполняет полное чтение и сверяет владельца, fingerprint токена,
UUID запуска и обязательные коллекции. Выводит только boolean-проверки и числа.
Перед каждым запуском backend такая же проверка выполняется до старта worker.

## Подготовка тестового каталога

```sh
docker compose --env-file "$LAB_ENV" -f compose.migration-lab.yaml \
  --profile tools run --rm --no-deps tools catalog --write
```

Набор согласован пользователем в плане приёмки: два новых наличных VND-счёта,
один USD-счёт, расходная категория, доходная категория и тестовый получатель.
Название содержит `ZenImport LAB` и сокращённый UUID запуска. Операций эта
команда не создаёт. Не назначать существующие счета целями последующих сценариев.

До первой записи сохраняется fsync-журнал `catalog.json`: полные UUID/payload,
владелец, запуск и исходные сущности. Конкурирующие процессы исключены flock.
После записи выполняется независимое чтение, проверяются счета/валюты/нулевые
балансы, категории и сохранность исходных сущностей. Повтор команды никогда
не отправляет catalog снова: только сверяет уже сохранённый intent. Неизвестный
результат останавливает приёмку. Автоматической очистки созданных сущностей нет.

## Запуск A и B

```sh
docker compose --env-file "$LAB_ENV" -f compose.migration-lab.yaml \
  --profile a up -d --no-build --wait server-a
docker compose --env-file "$LAB_ENV" -f compose.migration-lab.yaml stop server-a
docker compose --env-file "$LAB_ENV" -f compose.migration-lab.yaml \
  --profile b up -d --no-build --wait server-b
docker compose --env-file "$LAB_ENV" -f compose.migration-lab.yaml stop server-b
```

Сначала проверяются `/health`, авторизация, каталог и пустые таблицы банка,
заданий и попыток. Получение зеркала не должно создавать ни одного финансового
запроса. Серверы с непустой очередью нельзя запускать одновременно: flock
защищает только одну локальную БД, не разные серверы. Копировать БД только после
остановки A и через `backend.snapshot`, с проверкой целостности/владельца.

Остановка текущего лабораторного проекта:

```sh
docker compose --env-file "$LAB_ENV" -f compose.migration-lab.yaml \
  --profile tools --profile a --profile b down
```

SQLite и журнал остаются в приватном каталоге запуска. Не применять общий
Docker prune и не останавливать другие проекты. Если свободные диапазоны
Docker-сетей исчерпаны, сначала завершить собственное окружение и запускать
полные offline-проверки последовательно с лабораторией.

## Последующие этапы и критерии

1. **Контролируемая история.** Отдельная тестовая банковская страница и независимый
   эталон. Расход, приход, возврат, четыре направления долга, обе стороны обычного
   и валютного перевода, повторяющиеся суммы, разбивка и объединение, новая
   операция рядом с существующей. Устойчивые bank IDs, точное Decimal-движение,
   дата/время/часовой пояс; категории не являются частью идентичности платежа.
2. **С переносом БД.** Импорт через A; повтор без создающих запросов; правки/удаление
   только принадлежащих запуску записей; зеркало; остановка A; snapshot/restore B;
   переключение popup в отдельном Chrome-профиле; повтор прежнего периода; затем
   только новые операции. Сохранены прежние UUID и пользовательские изменения,
   удаление окончательно, каждая новая запись создаётся один раз.
3. **Пустая БД.** Независимый набор тестовых счетов. B впервые читает ZenMoney,
   распознаёт все типы и составные соответствия по банковской стороне, создаёт
   только положительную разницу количеств. Повтор не создаёт новых UUID. Затем
   отдельно измерить ограничения: удаление до знакомства сервера, изменение
   даты/суммы/счёта, посторонняя ручная запись с той же суммой, неоднозначные
   группы, два физических счёта с одной целью. Не скрывать невозможность
   восстановления потерянного журнала дополнительной эвристикой.
4. **Восстановление и Chrome.** Потеря ответа после записи, перезапуск, закрытие
   вкладки, замена токена, неизвестный job и новый tabId, запрет небезопасной смены
   сервера. Сначала fake API, затем явно запускаемый live transport. Проверить
   настоящий popup и отдельный профиль, HTTPS и выдачу host permission. Два
   localhost-адреса не доказывают приёмку внешнего HTTPS.
5. **Независимая сверка.** UUID, количество и число фактических создающих запросов,
   расходы/приходы и итог движения по каждому счёту/дню, обе валютные стороны,
   группы и удаления. Равного общего остатка недостаточно. Начальный остаток
   учитывать отдельно; ни один непроверенный результат не считать успехом.
6. **Публикация.** Только после отчёта: проверить историю Git на секреты/данные,
   выбрать лицензию, подготовить CI, wheel/sdist, ZIP, image-based Compose,
   ARM64/AMD64 и GHCR workflow с отдельным явным запуском. Рабочих токенов в CI
   нет. Коммиты локальные; push, Git-теги, публикация и рабочий переезд требуют
   отдельного разрешения.

## Проверки кода лаборатории

`scripts/test-docker.sh` включает `tests/test_migration_lab.py`, но не выполняет
живые запросы. Проверяются неверный/семейный пользователь, другой токен/запуск,
неполный снимок, рабочий токен/порт, права файлов, ограниченный каталог, intent
до запроса, потерянный ответ до/после применения, повтор без записи,
конкурирующий процесс и изменение исходных сущностей.

## Контролируемая история и последовательный A/B-прогон

Новый runner: `scripts/migration_replay.py`. Из корня backend:

```sh
python3 scripts/migration_replay.py --env-file "$LAB_ENV" --write
```

Перед первым запуском пересобрать tools-образ приведённой выше командой.
Контроллер принимает только сгенерированный каталог `.local/migration/<UUID>`;
использует отдельный Compose и loopback-порты. Единственный процесс удерживает
flock. Docker/API-ответы и контрольные точки сохраняются приватно. Для запросов
задания request_id/worker_id фиксируются до HTTP; потерянный ACK не приводит к
новой команде. При настоящем unknown результате запись не повторяется.
Состояние running с временным uncertain после intent ожидается до результата.

Два независимых набора: `migrated` и `empty`, по 3 счета VND/VND/USD.
Первый использует каталог предыдущего этапа; второму создаются собственные
3 счёта. Добавляется одна тестовая расходная категория для изменения категории.
На набор заранее создаются 18 записей ZenMoney, которым соответствуют 19
банковских записей; ещё две банковские записи отсутствуют в ZenMoney.
Банк-фикстура поступает через тот же публичный HTTP-контракт, что использует
сборщик расширения. Native bank-reference намеренно отсутствует: проверяются
счёт/день/знаковая сумма всех типов и составные соответствия.

Состав: расход/приход, покупка и возврат, неизвестная категория, две равные
суммы в день, lend/collect/borrow/repay, обе стороны VND/VND и VND/USD переводов,
одна банковская запись из двух ZenMoney (split), две банковские из одной
ZenMoney (merge), смешанный settlement. Две отсутствующие записи должны
создаться viewed=false. Позднее добавляются ещё расход VND и приход USD.

Перенесённая БД: A initial (2 новых), повтор A (0), затем через API имитируются
пользовательские правки категории/комментария и превращение нового расхода
в долг, одна собственная запись удаляется. После свежего зеркала A останавливается,
через backend.snapshot создаётся согласованный снимок B. На B прежняя история
не должна создавать записей; правки и удаление сохраняются. Затем две новые
записи и повтор без новых запросов.

Пустая БД: на A импортируется независимый набор (2 новых); после повтора
сервер B останавливается, прежняя его БД архивируется, создаётся пустой каталог.
Настройки счетов создаются заново, новая БД должна иметь другой instance_id.
Первый импорт и повтор B не должны создавать прежних операций. Затем две новые
записи и ещё один повтор. Архивы БД не удаляются.

Ожидания зафиксированы до запросов; seed/catalog intent сохраняется с fsync.
Повтор seed-шага только читает результат, не отправляет UUID заново.
Transport-обёртка регистрирует фактические исходящие write IDs до передачи HTTP;
не пишет токены, описания, суммы и ответы API. Верификатор независимо сверяет
точный набор UUID, поля каждого UUID, категории/непросмотренность, дневные
расходы и приходы, банковский net по каждой валютной стороне и остатки.
Отдельно проверяет виртуальный debt ledger и неизменность исходных сущностей.
При намеренном удалении банк сравнивается с явной поправкой на эту одну запись,
а отсутствие восстановления проверяется по UUID и нулю новых запросов.

Это приёмка реального тестового ZenMoney и настоящего backend HTTP/SQLite.
Chrome popup, банковский DOM, внешние HTTPS/host-permission и UI мобильного
приложения здесь не проверяются. API-имитация пользовательских изменений не
подменяет мобильную UI-приёмку. Пустой сценарий намеренно не получает удаления
до первого знакомства B: утраченный журнал не позволяет гарантированно
распознать такие удаления. Отчёт не должен обещать безопасность произвольного
сброса базы. Фактические итоги добавляются после завершения прогонов.
