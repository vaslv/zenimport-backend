## Проблема

Пользователь ведёт личные финансы в ZenMoney, но операции из трёх используемых им вьетнамских банков приходится вносить вручную. Требуется промежуточное приложение, которое сокращает ручной ввод, сохраняет возможность проверить результат и не создаёт повторные операции.

## Цель

Реализовать личную интеграцию «веб-кабинет банка → Chrome Extension → собственный backend → проверка → ZenMoney». Пользователь самостоятельно входит в банк и открывает нужный список операций. Приложение извлекает данные из уже открытой страницы, сохраняет их, сверяет с ZenMoney и отправляет только подтверждённые отсутствующие операции.

Целевой объём — три банка. Первый практически полезный MVP должен поддерживать один выбранный реальный банк и пройти проверку с живым ZenMoney. Затем подключаются остальные два. Названия банков пока не сообщены; упоминание Vietcombank в предыдущем обсуждении было примером, а не подтверждённым выбором.

## Основания и принятые решения

Документ объединяет доступный фрагмент предыдущего чата «Исследование API ZenMoney», текущий чат разработки и фактическое состояние файлов проекта. [Ссылка на предыдущий чат](chatgpt-conversation://6ac23078-d4b0-83ec-b054-467fccfc754a).

Пользователь запросил backend, расширение Chrome Manifest V3 и отдельный SPA-интерфейс внутри расширения. Парсинг выполняется локально. Полный HTML по умолчанию не отправляется; для диагностики нужен отдельный механизм. Исходные банковские данные и зеркало ZenMoney должны сохраняться независимо.

В первом обсуждении предлагался PostgreSQL. Для уже созданного личного skeleton выбран SQLite: пользователь разрешил практичный выбор стека. Это решение реализации, а не требование навсегда отказаться от PostgreSQL. Переход следует оценить при подготовке удалённого сервера.

Публичный API ZenMoney позволяет использовать diff вместо автоматизации его веб-интерфейса. Текущая реализация основана на [официальной документации API](https://github.com/zenmoney/ZenPlugins/wiki/ZenMoney-API), проверенной в ходе разработки. Живое подключение пока не проверялось.

## Обязательные уточнения пользователя

1. **Docker — основная среда исполнения backend и тестов.** Подготовить Dockerfile, Compose-конфигурацию и воспроизводимый запуск одного и того же приложения локально и на сервере. Зависимости и тестовые инструменты упаковать в соответствующие образы. Данные и очередь сохранять вне изменяемого слоя контейнера. Расширение работает в Chrome пользователя; для автоматической проверки расширения предусмотреть отдельное контейнерное браузерное окружение. Обычный запуск в `.venv` не заменяет приёмку в Docker.
2. **Нужна история банка, а не только последние операции.** Пользователь выбирает период в банковском кабинете. Поддержать сбор нескольких страниц/частей истории, прогресс, продолжение после прерывания и повторный импорт пересекающихся периодов. Выгружать только реально доступные через страницу данные и явно показывать ограничения полноты.
3. **История ZenMoney должна покрывать более длительный период.** Загрузить доступную историю за достаточный для сопоставления и категоризации период; его конкретные границы ещё не согласованы. Хранить историческое зеркало и затем поддерживать его инкрементально. Фактический охват данных проверить; один успешный diff не считать доказательством полноты истории.
4. **Использовать историю для подсказок категорий новых операций.** Сопоставлять старые банковские операции с уже категоризированными записями ZenMoney. Из подтверждённых связей получать примеры «банковский получатель и другие признаки → категория». Новым операциям предлагать категорию с объяснением и возможностью исправления. Это часть первого полезного MVP, а не необязательная задача после подключения всех банков.

Эти требования уточняют прежний план. Docker-упаковка и локальные контейнерные проверки выполнены; управляемый импорт истории и автоматические подсказки ещё не реализованы.

## Приоритет этапов по последнему уточнению пользователя

Сначала Docker, затем интерфейс Chrome Extension с локальным backend. После этого исследовать API ZenMoney и выбрать качественную библиотеку либо создать отдельный пакет клиента. Только затем спроектировать полноценную структуру БД для всех доступных согласованных данных API и загрузить историю ZenMoney. Далее — банковская история и отдельные таблицы, сопоставление и категоризация. Запись новых операций в ZenMoney — последний функциональный этап после проверки предыдущих.

Предварительный клиент, JSON-зеркало и outbox уже есть в skeleton, но не заменяют исследование, проектирование и приёмку этих этапов. Порядок в `docs/PLAN.md` имеет приоритет над прежней последовательностью.

## Пользовательский сценарий

1. Пользователь открывает веб-кабинет банка, выбирает исторический период и загружает нужные страницы операций; позднее тем же способом добавляет новые операции.
2. Нажимает иконку расширения; оно определяет банк и выбирает адаптер.
3. Адаптер локально извлекает исходные поля, нормализует суммы и даты, показывает итог сбора.
4. По команде пользователя пакет отправляется backend и сохраняется с указанием банка, счёта и версии адаптера.
5. В отдельной странице расширения пользователь загружает историю ZenMoney за длительный период, затем синхронизирует изменения и сопоставляет банковский счёт со счётом ZenMoney.
6. Интерфейс показывает банковские операции, существующие операции ZenMoney и кандидатов совпадений.
7. Пользователь связывает уже имеющуюся операцию, пропускает строку либо подтверждает создание. Проверяет категорию, предложенную на основании исторических примеров, либо выбирает её вручную.
8. Отдельная команда отправляет подтверждённые операции в ZenMoney.
9. Повторные импорт и отправка не должны создавать повторные записи. Неопределённый результат сети должен быть виден и разрешаться сверкой.

## Ограничения и правила

- Один владелец; многопользовательский сервис не входит в текущий объём.
- Вход в банк и загрузка страниц выполняются человеком. Не требуется автоматизация банковской авторизации.
- Банковские пароли, cookies и токены сессий не входят в импорт. ZenMoney token хранится на backend.
- Деньги хранятся целыми минимальными единицами; календарная дата банка не смещается преобразованием в UTC.
- Одинаковые сумма и дата не доказывают дубль. При отсутствии стабильного reference нужен отдельно спроектированный способ идентификации, а не молчаливое объединение строк.
- Переводы между своими счетами, hold/pending, обмен валют и сложные комиссии пока не поддерживаются как создаваемые операции. Их нельзя автоматически превращать в обычный расход или доход.
- Не создавать Git-теги и не выполнять push без отдельного явного разрешения пользователя. Общая задача разработки такого разрешения не даёт.
- Общение и документация — на русском.

Подробности устройства находятся в `docs/architecture.md`, контракт адаптеров — в `docs/adapters.md`.

## Готовность первого реального MVP

MVP считается принятым, когда операции одного выбранного банка корректно считываются через расширение в Chrome, сохраняются, сопоставляются с настоящими счетами ZenMoney и после проверки появляются в ZenMoney с правильными датами, суммами, знаком, счётом и категорией. Повторный импорт не создаёт дублей, а таймаут отправки не приводит к созданию новой операции с новым UUID.

До приёмки первого реального MVP также обязательны локальный прогон в Docker, сбор исторического периода первого банка, загрузка более длительной истории ZenMoney и проверка предложений категорий на новых операциях по подтверждённой истории. Исторический импорт сам по себе не должен отправлять старые операции обратно в ZenMoney: для этого по-прежнему требуется отдельное решение пользователя.

Поддержка остальных двух банков следует после первой приёмки. Нельзя считать её, полноту истории или качество подсказок подтверждёнными на основании demo-прогона.
