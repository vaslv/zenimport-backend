# Named bank connections

Status: local development 0.2.1. Pair with Chrome 0.2.1; no SDK change.
A bank may have many named connections, each identified by the stable
`(bank, profile_key)` pair. User-chosen profile keys are UUIDs generated by Chrome.
They identify access, not a bank password or financial account. No bank login,
password, cookies, or OTP fields are accepted or stored by this feature.

## API v1

All endpoints require the backend Bearer token. Requests remain subject to the
normal migration gate and body limits.

- `GET /api/v1/connections?bank=bidv` (or `vietinbank`) returns
  `ConnectionCatalog {connections: ConnectionView[]}` with all saved connections
  for that bank, including connections without currently linked accounts.
- `POST /api/v1/connections/discover` accepts optional `label`. Omitting it keeps
  the saved name. A new unnamed legacy connection gets a stable display fallback.
- `ConnectionView` adds `profile_key`, `profile_identity`, and `label`.
- `PUT /api/v1/connections/{id}/label` accepts `{ "label": "Personal" }`.
  Trimmed names contain 1–120 characters without control characters. Renaming
  changes no account identity, settings version, capture, or financial record.
- `POST /api/v1/connections/{id}/accounts/{account_id}/unlink` accepts `{}`.
  It marks that membership absent and invalidates that connection's account
  capture. It neither deletes financial data nor changes other memberships.

Discovery is idempotent by bank/profile key. Chrome queries the catalog before
associating bank observations; unknown accounts need an explicit association if
that bank already has a connection. Never infer access identity from an owner name.
The API token still authorizes the whole backend; names are not security tenants.

## Financial identity and settings

Each connection has its own observed account membership and jobs. Enabled/ignored
selection, ZenMoney mapping, initial date and coverage live on the canonical
physical account. Distinct accounts are independent even within the same bank.
Both current connectors prove bank-scoped account numbers. The same physical
account exposed by two logins therefore reuses one account UUID, one mapping and
one permanent delivery/deletion journal. Shared settings apply to all connections;
unlinking is the way to exclude that account from only one connection.

Unlinking preserves the historical connection-account association for audit, marks
its current discovery absent, and recomputes overall support from other present
memberships. Rediscovery can reattach the same identity. Existing delivery rules,
signed day/amount matching across all ZenMoney types, unread creation, and final
mobile edits/deletions are unchanged. There is no automatic send on discovery.

## Storage and migration

Schema 7 adds `connection_labels(connection_id, label)`. Existing connection,
account, delivery, UUID, coverage, and tombstone tables are unchanged. Upgrade
is transactional and makes the standard private pre-v7 backup, including WAL.
The current snapshot/export includes names and all memberships automatically.

The authenticated archive importer accepts schema 6 (published backend 0.2.0)
and current schema 7. It verifies the exact archive, hash, declared/actual schema,
SQLite ownership/integrity, instance identity and ZenMoney owners before upgrading
a private temporary copy. Import into the live destination remains a backup
transaction guarded by the original empty-destination and migration-hold rules.
Older binaries cannot read schema 7 or its archives; do not downgrade after upgrade.
No compatibility assumption relaxes checksum, identity or first-sync restrictions.

Docker tests use synthetic SQLite/banks/ZenMoney only. They check separate account
sets and jobs, rename/unlink isolation, shared identity/settings, existing schema-6
backup/upgrade, old archives, schema mismatch rejection, and named archive restore.
Real sequential-login acceptance and production rollout remain separate steps.
