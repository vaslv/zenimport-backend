# Хранилище ZenMoney v2 и длительная история

Реализовано 5 октября 2026. Это зеркало доступных данных diff API, не копия внутренней базы ZenMoney. Полнота реального аккаунта ещё не проверена.

## Слои и таблицы

| API | Таблица | Основные проекции и связи |
|---|---|---|
| instrument | zen_instrument | id, title, shortTitle→code, rate |
| company | zen_company | id, title, country→country_id |
| country | zen_country | id, title; принимается при наличии в ответе |
| user | zen_user | id, login, parent→parent_id, currency→currency_id |
| account | zen_account | id, user_id, instrument_id, company_id, title, type, archive, balance |
| tag | zen_tag | id, user_id, parent_id, title |
| merchant | zen_merchant | id, user_id, title |
| budget | zen_budget | составной API-ключ (user,date,tag), income, outcome |
| reminder | zen_reminder | id, user_id, start_date, end_date, income, outcome |
| reminderMarker | zen_reminder_marker | id, user_id, reminder_id, date |
| transaction | zen_transaction | id, user_id, date, счета/валюты обеих сторон, income/outcome/opIncome/opOutcome, merchant_id, payee/originalPayee, comment, hold |
| transaction.tag | zen_transaction_tags | transaction_id, tag_id, position; несколько категорий |
| deletion | zen_deletions | событие удаления, run_id, kind, entity_id, полный data |
| весь ответ | zen_sync_runs | requested_cursor, response_cursor, received_at, origin, payload |

В каждой таблице сущностей дополнительно: changed, deleted, полный data и run_id. Любое поле API, не перечисленное в проекции, остаётся в data и неизменённом тексте исходного ответа. Любая неизвестная коллекция остаётся в архиве ответа, но не превращается молча в выдуманную таблицу. Словарь `FIELDS` в `backend/zenstore.py` — исполняемая матрица поле→колонка; расширяется отдельной миграцией при необходимости.

`zen_entities` пока сохраняется как совместимый индекс для демонстрационных matching/outbox. Он обновляется в той же транзакции. Новая история и статистика используют структурированные таблицы. На этапе 6 matching должен перейти к индексированным проекциям с точными Decimal, а не обходить JSON-зеркало.

Связи между удалёнными справочниками логические, nullable: diff может прийти частично, ссылка может указывать на архивный или уже удалённый объект. Жёсткий FK используется внутри нашего слоя transaction→transaction_tags с каскадным удалением. Отсутствующий справочник не приводит к потере всей транзакции. Банковские таблицы остаются независимыми.

## Типы

Идентификаторы — TEXT, включая числовые id справочников. Деньги API — точный Decimal в TEXT: число `12.250000000000000001` не превращается в binary float при проекции. Значения извлекаются из исходного JSON с `parse_float=Decimal`. Для исходного JSON важен архив payload; повторно сериализованный data сам по себе не гарантирует лексическую точность чисел. API истории отдаёт `_amounts` как строки для отображения.

Банковские amount_minor пока целочисленные. Валюты истории ZenMoney не ограничены VND/USD/EUR; ограничения demo-импорта независимы. Календарные даты — проверенный ISO `YYYY-MM-DD`; timestamps — целые значения API. Не выполняется перевод календарных дат в UTC. Неизвестное поле не теряется; неправильный тип используемого поля останавливает diff целиком.

## Синхронизация, архив и сбои

1. На первой загрузке запросить cursor=0 и документированные forceFetch-коллекции. Фильтрация по периоду применяется к локальному просмотру, не обрезает выгрузку.
2. Валидировать ответ, записать исходный текст, обновить сущности, связи и удаления.
3. В той же SQLite-транзакции сохранить новый cursor. Ошибка записи, некорректная сущность или прерывание откатывают всё.
4. Следующий sync продолжает с последнего успешного cursor. Операции повторного diff обновляются по стабильным ключам без дублей; архив хранит каждый успешно принятый ответ.

Удаление через deletion убирает актуальную сущность и оставляет событие/старую версию в архиве. `transaction.deleted=true` сохраняется как версия, скрытая в обычной истории; её можно запросить `include_deleted=true`. Составной формат deletion для budget не подтверждён: такой ответ явно отклоняется без сдвига cursor до появления реального fixture. Это ограничение, а не незаметная потеря бюджета.

Миграция v1→v2 атомарно создаёт проекции из существующего JSON-зеркала, сохраняет банки/очередь/cursor, помечает архив `migration-v1`. Предыдущие версии отсутствовавших ответов не реконструируются. Мигрированная непустая база получает `needs_full_sync`, чтобы следующий запрос cursor=0/forceFetch забрал исторические данные новых коллекций, а не только их будущие изменения. При неудаче флаг сохраняется. Неизвестная будущая версия схемы запрещает запуск. Downgrade не поддержан; перед обновлением реальной базы нужен резервный снимок.

Повторная полная загрузка не удаляет локальную сущность только из-за отсутствия её в ответе: удаления требуют явного события/флага API. Этот консервативный контракт необходимо проверить на реальном аккаунте при первичной приёмке.

## Просмотр и проверка полноты

`GET /api/zenmoney/history`: limit 1–200, offset≥0, start/end включительно, account, include_deleted. Сортировка date DESC/id, значения SQL параметризованы. `GET /api/state` содержит первые 100 операций и общую статистику, а не всю историю. SPA показывает страницы по 100, период и диапазон реально имеющихся дат. При параллельной синхронизации offset-страницы не являются замороженным снимком; после sync список следует обновить.

Минимальная и максимальная даты — наблюдаемый диапазон, не доказательство полноты. `coverage_verified=false` честно отражает отсутствие сверки. В документации diff нет обещания произвольного архива удалённых операций, банковских вложений или всех внутренних таблиц. Запрашиваем всю доступную историю, затем сверяем выбранный период с приложением ZenMoney: счета, количества/итоги по месяцам, известные крайние операции. Желаемый период пока не назван.

## Объём и эксплуатация

Для личного приложения пока оставлена SQLite WAL: один worker, транзакции, индексы даты, счетов, получателя и merchant. PostgreSQL потребуется при нескольких пользователях/worker, фоновых параллельных заданиях или измеренной нехватке производительности. Смена БД ради контейнера не нужна.

Тест использует 1 200 операций разных дат и проверяет границы страниц/фильтров; это функциональная проверка, не нагрузочный benchmark пользовательской базы. Ответ ограничен 64 МиБ, JSON несколько раз размещается в памяти; реальный лимит объёма определится по данным. Сеть пока выполняется внутри транзакции и блокирует другие записи. Архив растёт с каждым sync, автоматической очистки нет. Для серверного запуска ещё нужны согласованные резервные копии, retention и измерение объёма.
