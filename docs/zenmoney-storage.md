# Хранилище ZenMoney — схема 12

Схема 12 дополняет проекции API локальными определениями типов операций и
проверяемыми намерениями отправки: `bank_operation_drafts`,
`zen_operation_drafts`, `zen_operation_sends`. Все прежние таблицы сохраняются.
Подробности: [operation-types.md](operation-types.md).

Обновлено 14 октября 2026. Это зеркало публичного diff API, не копия внутренней
базы сервиса. Структуры соответствуют моделям SDK 0.6.0; неизвестные поля остаются
в полном JSON сущности, неизвестные коллекции — в исходном ответе.

Исполняемая матрица всех полей — FIELDS в backend/zenstore.py. Тест сравнивает её
с полями моделей SDK, чтобы новые поля библиотеки нельзя было незаметно пропустить.
Budget.id — внутреннее точное JSON-представление составного API-ключа; исходный
объект Budget не получает выдуманный id. Nullable tag сохраняется.

zen_entities удалена: текущие данные читаются непосредственно из таблиц сущностей.
Банковские таблицы, группы сопоставления many-to-many, категории/правила и очереди
отправки остаются прикладным слоем; их идентификаторы и состояния сохраняются.

## Типы и точность

Идентификаторы в SQL — TEXT, включая числовые системные ID; полный JSON сохраняет
исходный API-тип. Денежные суммы, курсы, проценты и координаты — Decimal в TEXT;
SQLite REAL не используется. Timestamp/integer/boolean — INTEGER; nullable остаётся
NULL. syncID/points — JSON массивы, категории движений — отдельные таблицы.

Все внутренние JSON-границы используют точную сериализацию. HTTP endpoints
возвращают Response напрямую: FastAPI не переводит Decimal во float до ответа.
JSON-сумма остаётся числом; история дополнительно возвращает точные текстовые
_amounts. JavaScript Number имеет собственные ограничения точности, поэтому эти
строки доступны для отображения и внешних клиентов.

Ссылки между удалёнными справочниками логические: diff может прийти частично,
объект может быть удалён или архивирован. Отсутствующая категория/счёт не уничтожает
всю операцию. Внутренние таблицы Movement→tags используют FK с ON DELETE CASCADE;
индексы есть по датам, счетам, получателю, merchant, валютам/владельцам и категориям.

## Синхронизация

Одна транзакция сохраняет raw diff, проекции/категории, удаления и cursor.
Soft-deleted Transaction сохраняется, но исключается из обычной истории/matching.
Hard deletion удаляет текущую запись и её категории; архив остаётся.
Явный forceFetch с полученной коллекцией удаляет также отсутствующие в полном
снимке записи. Инкремент и отсутствующая в ответе коллекция так не обрабатываются.
Неизвестное удаление сохраняется в журнале. Неоднозначное удаление Budget не
угадывается: публичный SDK очищает бюджет через суммы/locks, не delete по UUID.

GET /api/zenmoney/history предоставляет limit/offset, период, счёт и include_deleted.
/api/state содержит первые 100 записей и сводку. Минимальная/максимальная даты и
coverage_verified=false не доказывают полноту истории сервиса.

## Миграция и эксплуатация

Перед миграцией initialize создаёт SQLite backup рядом с БД с именем
*.pre-v11-<UTC>-<suffix>.sqlite3, правами 0600. Backup включает WAL.
Затем в одной транзакции добавляются колонки и связи; текущие объекты восстанавливаются
из **своих** архивных ответов, без восстановления уже hard-deleted записей.
Парсится один архивный ответ за раз. При отсутствии исходного ответа сохраняется
текущий объект и ставится needs_full_sync. Cursor не теряется.

Неотправленные prepared/queued payload получают SDK defaults с прежним UUID.
Попытки uncertain/sent остаются неизменными. При любой ошибке новая версия схемы
не фиксируется; резервная копия остаётся для диагностики/восстановления.

SQLite WAL, один worker, отдельные DEMO/LIVE volumes. Сеть при sync пока выполняется
в транзакции и блокирует другие изменения. Архив растёт при каждом чтении; retention
и переход на PostgreSQL не входят в эту миграцию. Backup находится в том же volume:
для защиты от потери диска нужна отдельная внешняя копия.
