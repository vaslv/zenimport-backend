# ZenImport — согласованный порядок разработки

Обновлено: 7 октября 2026. Последнее уточнение пользователя определяет порядок этапов ниже. Уже созданный сквозной skeleton используется как прототип и источник тестов; наличие кода не означает приёмку соответствующего этапа. Исторические данные, Docker и категоризация остаются обязательными требованиями.

## Этапы и зависимости

| № | Этап | Статус | Условие перехода дальше |
|---|---|---|---|
| 1 | Запуск и тестирование в Docker | Выполнен локально в DEMO | Образ собирается, тесты проходят, данные переживают пересоздание |
| 2 | Интерфейс расширения Chrome + локальный backend | Выполнен в Docker/Chromium | Подключение, настройки, состояния и ошибки проверены с MV3 |
| 3 | Клиент API ZenMoney: библиотека или отдельный пакет | Пакет и live-чтение проверены | Выбран и проверен поддерживаемый контракт чтения API |
| 4 | Структура БД и загрузка данных ZenMoney | Схема v2 и история реализованы; live-полнота не проверена | Спроектирована схема всех согласованных сущностей и загружена история |
| 5 | Получение истории банков и отдельное хранение | VietinBank реализован и проверен на fixtures; реальный импорт ожидает расширение | Проверен импорт истории реального банка без потерь и дублей |
| 6 | Сопоставление и категории по истории | Реализованы единый список, локальные связи и подсказки; нужна пользовательская приёмка | Проверены связи и объяснимые подсказки для новых операций |
| 7 | Запись новых операций в ZenMoney | Есть демонстрационный outbox | Все предыдущие этапы приняты; подтверждённая запись проверена отдельно |

Живую запись через ZenMoney API не выполнять до этапа 7. Демо-тесты прежнего outbox на этапе 1 проверяют сохранность каркаса, но не являются началом внедрения живой записи.

- [x] Оценить SQLite/PostgreSQL по данным и потребностям, а не менять БД только ради Docker.
- [ ] Согласовать длительный период истории; проверить фактическую полноту первой загрузки и документированные ограничения API.

## 6. Сопоставление и категории

- [ ] Проверить привязку bank_account ↔ zenmoney_account и ограничения валюты/истории.
- [ ] Сопоставить старые банковские операции с уже существующими транзакциями ZenMoney, показать основания кандидатов и неоднозначность.
- [ ] Хранить подтверждённые связи, использованные признаки и категорию, учитывать изменения/удаления в источнике.
- [x] Для новых операций предлагать категории по точному получателю или описанию из более ранних исторических примеров.
- [x] Разделять поиск дубля и похожего примера: категория не требует той же суммы и близкой даты.
- [ ] Показывать основание и уверенность рекомендации, позволять исправление, не обучаться на неподтверждённых собственных подсказках.
- [ ] Проверить качество на более поздней части истории, используя только более ранние примеры. Численный порог согласовать после изучения данных.

Историческая загрузка и сопоставление не отправляют новые записи в ZenMoney.

## 7. Запись в ZenMoney — последний функциональный этап

- [ ] Пересмотреть демонстрационный outbox с учётом окончательных API-клиента и схемы БД.
- [ ] Реализовать явные review/confirm и устойчивую очередь с UUID и неизменяемым payload.
- [ ] Проверить повторную сверку перед отправкой, потерю ответа после записи, перезапуск, изменение удалённой записи и конфликты.
- [ ] На конкретных согласованных пользователем операциях проверить live-создание, правильность счёта/суммы/даты/категории и отсутствие дублей.
- [ ] Завершить сквозную приёмку: исторический импорт → связи → новые операции → подсказки → подтверждённая запись.

Переводы между своими счетами, валютный обмен и другие сложные типы не превращать в обычные доходы/расходы; добавлять отдельными задачами.

## Серверное развёртывание и остальные банки

Docker-подготовка выполняется первой. Фактическое развёртывание, HTTPS, резервное копирование и восстановление проверяются на согласованном сервере отдельным шагом готовности. Второй и третий банки проходят этапы 5–7 по тому же контракту. Публикация образов, push и Git-теги требуют соответствующего явного разрешения.

## Уточнение сценария: одно меню и история для обучения (6 октября 2026)

- Основной способ VietinBank — JSON истории. В popup один основной путь: период → получение → локальное сохранение → проверка. Старые DOM-инструменты и файл доступны только в свёрнутой диагностике.
- Режимы: последний месяц для регулярного обновления; последние 6 месяцев для первичного сопоставления. Сейчас это подсказка точных календарных дат, выбранных в часовом поясе Вьетнама: фильтры применяются в банке вручную. Не выдавать подсказку за автоматическое управление периодом.
- До автоматизации шестимесячной загрузки проверить реальные параметры запроса, ограничения диапазона и пагинацию. Собирать страницы/отрезки с метаданными покрытия, проверять пропуски и повторы; currentPage/pageSize не равны страницам таблицы. Не объявлять импорт полным по одной странице 100/135.
- Исторические операции сопоставлять с уже существующими записями ZenMoney. Оператор просматривает кандидатов и явно подтверждает связь. Несколько кандидатов и отсутствие совпадения требуют проверки, а не автоматического создания.
- Предлагать связь «получатель → категория» по подтверждённым историческим соответствиям. Показывать получателя, категорию, подтверждающие примеры и конфликтующие категории. Пользователь принимает или исправляет правило; неподтверждённые предложения не становятся обучающими данными.
- Для новых операций разделять поиск дублей и предложение категории. Показывать основания предложения; пользователь может изменить категорию, связать существующую запись, пропустить или подтвердить создание.
- Подтверждение локального решения и отправка в ZenMoney — разные действия. Перед отправкой показывать очередь изменений и повторно проверять дубли. LIVE-запись остаётся выключенной до реализации и проверки этого этапа.
