# ZenImport — согласованный порядок разработки

Обновлено: 5 октября 2026. Последнее уточнение пользователя определяет порядок этапов ниже. Уже созданный сквозной skeleton используется как прототип и источник тестов; наличие кода не означает приёмку соответствующего этапа. Исторические данные, Docker и категоризация остаются обязательными требованиями.

## Этапы и зависимости

| № | Этап | Статус | Условие перехода дальше |
|---|---|---|---|
| 1 | Запуск и тестирование в Docker | Выполнен локально в DEMO | Образ собирается, тесты проходят, данные переживают пересоздание |
| 2 | Интерфейс расширения Chrome + локальный backend | Выполнен в Docker/Chromium | Подключение, настройки, состояния и ошибки проверены с MV3 |
| 3 | Клиент API ZenMoney: библиотека или отдельный пакет | Пакет реализован; live-чтение ожидает токен | Выбран и проверен поддерживаемый контракт чтения API |
| 4 | Структура БД и загрузка данных ZenMoney | Схема v2 и история реализованы; live-полнота не проверена | Спроектирована схема всех согласованных сущностей и загружена история |
| 5 | Получение истории банков и отдельное хранение | Только demo-адаптер | Проверен импорт истории реального банка без потерь и дублей |
| 6 | Сопоставление и категории по истории | Есть прототип matching | Проверены связи и объяснимые подсказки для новых операций |
| 7 | Запись новых операций в ZenMoney | Есть демонстрационный outbox | Все предыдущие этапы приняты; подтверждённая запись проверена отдельно |

Живую запись через ZenMoney API не выполнять до этапа 7. Демо-тесты прежнего outbox на этапе 1 проверяют сохранность каркаса, но не являются началом внедрения живой записи.

## 1. Docker — выполнен локально

- [x] Добавить Dockerfile с отдельными runtime и test targets, Compose и `.dockerignore`.
- [x] Использовать один образ backend локально и на сервере; конфигурацию передавать окружением.
- [x] Создавать локальный API-токен без установки Python на хост и без вывода секрета в логи.
- [x] Запускать backend от непривилегированного пользователя, хранить БД и outbox в постоянном томе.
- [x] Проверить healthcheck, опубликованный локальный порт и остановку контейнера.
- [x] Прогнать серверные и JS-тесты в контейнерах, а также HTTP-проверку отдельного Compose-сервиса.
- [x] Проверить сохранность очереди, UUID, привязки и импортов после пересоздания контейнера.
- [x] Разделить обычные данные и одноразовые данные тестового проекта.
- [x] Документировать запуск, остановку, пересборку, тесты и ограничения.

Результаты зафиксированы в `docs/acceptance.md`. Критерий: запуск и проверки воспроизводятся с Docker/Compose без Python и Node на хосте. Само расширение работает в Chrome пользователя. Сборка production-образа на сервере и публикация образа не входят в этот локальный шаг.

## 2. Интерфейс расширения с локальным backend

- [x] Развить существующие MV3 popup и отдельную SPA без обязательной смены стека.
- [x] Проверить сохранение адреса/API-токена, доступ к backend в Docker и отображение состояния соединения.
- [x] Сделать понятными загрузку, отсутствие данных, недоступность сервера, неверный токен и повтор запроса.
- [x] Проверить раздельные экраны данных ZenMoney, банковских данных и review на демонстрационных данных.
- [x] Отделить готовые действия от возможностей следующих этапов; не представлять demo-банки и live-запись как принятые интеграции.
- [x] Пройти сценарий MV3 в Chromium (Playwright в Docker) и записать фактические результаты в `docs/acceptance.md`.

Для этого этапа не нужны реальные банковские парсеры или живой ZenMoney.

## 3. Клиент API ZenMoney

- [x] Изучить актуальную официальную документацию и составить список сущностей и операций API.
- [x] Найти подходящие библиотеки; оценить совместимость с Python, лицензию, поддержку, покрытие API, тесты, OAuth, обработку ошибок и качество моделей.
- [x] Зафиксировать решение в `docs/zenmoney-client.md`: библиотека и версия либо обоснование отдельного пакета.
- [x] Если подходящей библиотеки нет — вынести клиент в отдельный тестируемый пакет, независимый от FastAPI, SQLite и банковских адаптеров. Публикация пакета не требуется.
- [x] Отделить транспорт, модели, ошибки и авторизацию от хранения состояния приложения.
- [x] Проверить чтение, первичную/инкрементальную синхронизацию, удаления, таймауты и недействительный токен.
- [x] Определить OAuth onboarding/refresh и требования к хранению токенов.

Решение и ограничения: `docs/zenmoney-client.md`. Проверки контрактные, live-чтение и OAuth onboarding ожидают credentials. `backend/zenmoney.py` теперь адаптер отдельного пакета. На этом этапе работа с реальным API ограничена чтением. Контракт методов записи можно описать, но проверять живую запись — только на этапе 7.

## 4. База и полная история ZenMoney

- [x] После инвентаризации API составить матрицу «сущность/поле → таблица/связь/способ обновления». Не ограничиваться текущими account/tag/transaction/instrument/user.
- [x] Зафиксировать, что API действительно позволяет получить; недоступные данные явно обозначить. Не обещать выгрузку внутренней БД ZenMoney целиком.
- [x] Выбрать окончательную схему и типы: ключи, связи, валюты, деньги, даты, категории, контрагенты, удаления и служебные сущности.
- [x] Определить хранение исходных ответов отдельно от структурированных сущностей, версионирование и миграции.
- [x] Оценить SQLite/PostgreSQL по данным и потребностям, а не менять БД только ради Docker.
- [ ] Согласовать длительный период истории; проверить фактическую полноту первой загрузки и документированные ограничения API.
- [x] Реализовать атомарное применение diff/cursor, повторную загрузку, восстановление после прерывания, обновления и удаления.
- [x] Проверить ограничения памяти/размера, выборки и отображение истории в интерфейсе.

Схема и ограничения: `docs/zenmoney-storage.md`. Автотесты используют fixtures; реальная полнота и глубина истории ожидают подключения аккаунта. `zen_entities` сохранена как совместимый индекс demo-matching.

## 5. Банковские данные в отдельных таблицах

- [ ] Получить названия трёх банков, точные домены и порядок подключения.
- [ ] Получить обезличенные образцы истории, сведения о reference, счетах, получателе, датах, суммах, пагинации и доступной глубине.
- [ ] Спроектировать отдельные банковские таблицы и метаданные импортов, сохранив независимость от зеркала ZenMoney.
- [ ] Для первого банка реализовать определение страницы и локальный разбор по проверенным fixtures.
- [ ] Добавить сессии исторического импорта: запрошенный период, обработанные части, фактический охват, прогресс и продолжение после прерывания.
- [ ] Проверить пересекающиеся периоды, повтор страницы, разные операции с одинаковой суммой и изменённые reference.
- [ ] Не передавать полный HTML, cookies и токены. Хранить исходные поля и нормализованные признаки раздельно.

Не скрывать недоступные периоды или неподдержанные типы. Обход истории через доступную страницу либо ручная загрузка частей выбирается по устройству банка. Названия банков пока не известны.

## 6. Сопоставление и категории

- [ ] Проверить привязку bank_account ↔ zenmoney_account и ограничения валюты/истории.
- [ ] Сопоставить старые банковские операции с уже существующими транзакциями ZenMoney, показать основания кандидатов и неоднозначность.
- [ ] Хранить подтверждённые связи, использованные признаки и категорию, учитывать изменения/удаления в источнике.
- [ ] Для новых операций предлагать категории по получателю, назначению и другим доступным признакам исторических примеров.
- [ ] Разделять поиск дубля и похожего примера: категория не требует той же суммы и близкой даты.
- [ ] Показывать основание и уверенность рекомендации, позволять исправление, не обучаться на неподтверждённых собственных подсказках.
- [ ] Проверить качество на более поздней части истории, используя только более ранние примеры. Численный порог согласовать после изучения данных.

Историческая загрузка и сопоставление не отправляют новые записи в ZenMoney.

## 7. Запись в ZenMoney — последний функциональный этап

- [ ] Пересмотреть демонстрационный outbox с учётом окончательных API-клиента и схемы БД.
- [ ] Реализовать явные review/confirm и устойчивую очередь с UUID и неизменяемым payload.
- [ ] Проверить повторную сверку перед отправкой, потерю ответа после записи, перезапуск, изменение удалённой записи и конфликты.
- [ ] На конкретных согласованных пользователем операциях проверить live-создание, правильность счёта/суммы/даты/категории и отсутствие дублей.
- [ ] Завершить сквозную приёмку: исторический импорт → связи → новые операции → подсказки → подтверждённая запись.

Переводы между своими счетами, валютный обмен и другие сложные типы не превращать в обычные доходы/расходы; добавлять отдельными задачами.

## Серверное развёртывание и остальные банки

Docker-подготовка выполняется первой. Фактическое развёртывание, HTTPS, резервное копирование и восстановление проверяются на согласованном сервере отдельным шагом готовности. Второй и третий банки проходят этапы 5–7 по тому же контракту. Публикация образов, push и Git-теги требуют соответствующего явного разрешения.

## Рабочий порядок

Обновлять статусы по наблюдаемым результатам. Сохранять существующий код, но не считать прототип будущего этапа готовой функцией. Не перескакивать от Docker к банковским парсерам или live-записи. Документацию API/библиотек проверять через Context7 и официальные источники. Пользовательское общение — на русском.
