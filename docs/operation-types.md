# Типы операций — расширение 0.13.0, схема БД 12

В строках истории VietinBank и в ZenImport («Банки», «Операции», история
ZenMoney) доступна форма **«Тип операции»**. Она работает с новыми банковскими
записями и с уже существующими записями ZenMoney. Сумма, дата и исходный
банковский счёт фиксированы. Для существующей записи сохраняются UUID, время
создания, комментарий и остальные поля API.

## Что выбирать

| Тип | Направление на банковском счёте | Дополнительные параметры |
|---|---|---|
| Расход | Списание | Расходная категория |
| Приход | Поступление | Доходная категория |
| Возврат покупки | Поступление | Категория исходного расхода, только расходная |
| Перевод между счетами | Любое | Второй обычный счёт; для другой валюты — сумма на втором счёте |
| Дать в долг | Списание | Человек |
| Взять в долг | Поступление | Человек |
| Вернуть долг | Списание | Человек |
| Получить возврат долга | Поступление | Человек |

Несовместимые с направлением платежа варианты отключены. Переводы не имеют
категории. Счета должны быть активными и принадлежать пользователю или его семье.
Перевод в одной валюте сохраняет одинаковые суммы; при разных валютах нужно
ввести фактическую сумму во второй валюте. Decimal сохраняется точно, VND —
целое число. Неизвестный курс автоматически не вычисляется.

Долги используют имеющийся системный `type=debt` счёт ZenMoney, валюту движения
и имя человека (`payee`, `originalPayee`). Если уже есть однозначно известный
контрагент, сохраняется его `merchant`. При отсутствии или неоднозначности
системного долгового счёта сохранение блокируется с объяснением.

Публичный API не различает отдельным полем «дать» и «вернуть» долг, а также
«взять» и «получить возврат»: это направления движения между обычным и долговым
счетами. Приложение сохраняет выбранное действие в локальной истории. Для старых
записей без этой истории показывает направление как «дать»/«взять»; пользователь
может уточнить его. Возврат покупки передаётся положительным приходом в чисто
расходную категорию; отрицательные суммы в API не отправляются.

## Сохранение и общая отправка

1. Откройте форму, выберите тип и заполните параметры. Для категории доступны
   поиск и приоритетные подсказки по истории.
2. Нажмите **«Сохранить параметры»**. Это только локальный черновик, переживающий
   перезапуск backend. На банковской странице обновится локальный статус.
3. В ZenImport в выбранном банке нажмите **«Просмотреть все изменения»**.
   Либо откройте меню расширения на банковской вкладке и нажмите
   **«Отправить обновления в ZenMoney»**. В истории ZenMoney общая кнопка
   предлагает изменения типов существующих записей; прежняя отправка категорий
   остаётся доступной отдельно.
4. В общем окне просмотрите создаваемые записи и изменения существующих:
   тип, суммы обеих сторон, счета, валюты, категории и человека. Снимите флажки
   с записей, которые пока не нужно отправлять. Одна смешанная отправка — до
   20 изменений. Отмена просмотра ничего не отправляет.
5. Только кнопка **«Отправить в ZenMoney»** выполняет запись. Получение свежих
   данных перед ней проверяет, что подтверждённый просмотр не устарел. После
   записи backend отдельно получает фактические данные и подтверждает результат.

Изменение типа существующей записи заменяет локальный черновик категории этой
записи, чтобы не отправить два конкурирующих обновления одного UUID. Если
выбранный тип уже сохранён, дальнейшие категории меняются в этой же форме.
При неподтверждённой отправке сначала требуется **«Проверить изменения»**
или проверка результата из меню расширения. Автоматических повторов нет.

Перевод с двумя импортированными банковскими сторонами может быть связан с одним
UUID ZenMoney. Новая запись второй стороны не создаётся: предложение соответствия
требует подтверждения. Отмена одной локальной связи сохраняет другую сторону.
Изменение существующей записи не может нарушить суммы любого связанного
банковского счёта, включая составные группы и обе стороны перевода.

## Хранение и HTTP

Схема 12 добавляет `bank_operation_drafts`, `zen_operation_drafts`,
`zen_operation_sends`. Существующие банковские операции, зеркала API, архивы,
группы, категории и очереди не переписываются. При обновлении схемы создаётся
резервная SQLite-копия с правами 0600 до миграции.

- `PUT /api/new-operations/{bank_id}/operation`
- `PUT /api/zenmoney/transactions/{zen_id}/operation`
- `POST /api/operation-updates/preview`, `/send`, `/verify`
- `POST /api/batch/preview`, `/send`, `/verify` для общей отправки банка

Локальный PUT принимает `definition` и `expected_snapshot`. Definition содержит
`kind`, `account_id`, `category_id`, `other_account_id`, `other_amount`, `payee`.
Сумму другой валюты рекомендуется передавать десятичной строкой. Content script
может сохранить только решение для операции активного банковского счёта;
отправка в ZenMoney выполняется из доверенной страницы расширения.

## Проверка в Docker

`sh scripts/test-docker.sh` запускает backend, parser, браузерные и HTTP-тесты
с пересозданием контейнера. Дополнительный `operation-backend` использует настоящий
HTTP backend в LIVE режиме с синтетическим SDK-клиентом. Он изолирован от
пользовательской БД и не получает токен ZenMoney; его test-only маршруты никогда
не включаются в runtime-образ.

Проверяются все восемь типов для новых и существующих записей, Decimal и валюты,
направление, семейные/архивные счета, сохранение UUID, конфликт свежих данных,
потеря ответа, частичное применение, сохранность связей, локальное сохранение
в банковской строке, просмотр, отмена и подтверждение в установленном MV3.
