# ZenImport внутри VietinBank

## Согласованный сценарий

После входа и перехода в историю расширение получает актуальные данные ZenMoney,
сохраняет банковские ответы в локальную БД и показывает статусы рядом с операциями.
Локальная история остаётся источником подсказок. Однозначная категория выбрана заранее;
несколько вариантов представлены ссылками через запятую в порядке частоты, полный
список доступен с поиском. Выбор сохраняется локально. Отправка — отдельным действием
из меню расширения с общим предварительным просмотром и подтверждением.

## Реализованный первый этап (0.11.2)

- Однократная кнопка «Включить ZenImport на странице банка» запрашивает доступ только
  к https://ipay.vietinbank.vn/* и регистрирует persistent content scripts.
- На /payment-history?accountNo=… автоматически выполняется read-only sync ZenMoney.
  Сначала читаются сохранённые данные backend. Ошибка sync не скрывает их; повтор
  запускается автоматически с увеличением интервала от 30 секунд до 5 минут.
  Ошибка показана только в общем индикаторе. Для отсутствующей строки резервируется
  пустая полоса с небольшим индикатором во время загрузки.
- MAIN-наблюдатель перехватывает только существующие ответы getHistTransactions,
  копирует разрешённые поля. Не читает заголовки, запросы, токены и cookies.
- ISOLATED-скрипт связывает строку с БД по счёту, точному времени, описанию,
  подписанной сумме и остатку. Неоднозначные строки не получают редактора.
- Новые операции и простые подтверждённые связи поддерживают локальное назначение
  категории; подсказки кликабельны. Сложные связи открываются в существующем приложении.
- Блоки оформлены внутри Shadow DOM в дополнительной строке с colspan=4 под
  банковской операцией. Статус, подсказки и категория расположены горизонтально.
  MutationObserver добавляет каркас сразу при появлении строки, до завершения sync.
  Поиск находится внутри раскрытого списка; клик снаружи и Escape закрывают список.
  Клики по категории не открывают банковскую модальную форму.
- Переключение счёта/выход из истории удаляет блоки. Устаревшие ответы отбрасываются.
- Worker проверяет отправителя, верхний frame, действующий URL, счёт и принадлежность
  редактируемой записи. Произвольных API-путей в сообщениях нет. Ни одно сообщение
  от банковской страницы не запускает отправку в ZenMoney.
- Журнал последних 120 действий: время, тип, успех, длительность; без финансового
  содержимого. Включён в существующий экспорт диагностики.

## Проверка на реальной странице — следующий шаг

Обновить расширение, нажать кнопку включения, затем обновить вкладку банка и открыть
историю. Проверить реальную разметку, изменение фильтра и пагинацию, новые операции,
статусы связей и выбор категории. Сначала сверить несколько строк с реквизитами банка.
Не выполнять реальную отправку при этой проверке.

Ограничения первого этапа: проверена английская таблица DATE / DESCRIPTION / AMOUNT /
BALANCE; модальное окно банка пока не дополнено; общая кнопка пакетной отправки реализована в версии 0.12.0 (см. ниже). Существующие функции отправки приложения сохранены. Данные о строке,
не полученной из JSON и отсутствующей в БД, не угадываются: предлагается дождаться
ответа банка. Для продолжения JSON с totalRecords=0 требуется первая страница той же
последовательности; после перезапуска worker нужно повторить поиск в банке.

## Первоначальный план следующих этапов (отправка реализована в 0.12.0)

1. Подтвердить привязку на живой истории и собрать обезличенные фикстуры различий.
2. Добавить счётчик и общую форму просмотра обновлений в меню расширения.
3. Объединить создание и обновление категорий в одну контролируемую пачку на backend;
   сохранить durable intent, проверку свежих данных, защиту от повторной отправки
   и независимую проверку результата. Ограничение размера пачки сделать явным.
4. Показывать результаты отдельно для каждой операции, включая частичный успех.
5. Протестировать смешанную пачку, конфликт, потерю ответа и восстановление после
   перезапуска на искусственном API, затем выполнить согласованный живой тест.

## Версия 0.12.0: общая отправка и сессия

В меню расширения появилась кнопка «Отправить обновления в ZenMoney». Она берёт
счёт из активной банковской истории и открывает отдельную вкладку расширения с
модальным просмотром. Backend получает свежие данные, создаёт только допустимые
локальные записи с категорией, включает изменения категорий того же счёта.
Просмотр не отправляет изменения в ZenMoney. Неподходящие записи блокируются;
операции без категории не создаются. Лимит — 20 выбранных изменений на запрос.

`/api/batch/preview`, `/api/batch/send`, `/api/batch/verify` принимают обязательные
bank/account. Отправка повторно проверяет свежие данные и snapshots всей выбранной
пачки до записи. Намерения обоих типов сохраняются одной транзакцией SQLite в
существующих creation_jobs/zen_category_sends; миграция не нужна. Клиент проверяет
полезную нагрузку и отправляет один diff с обеими разновидностями записей.
Ответ записи не считается подтверждением: независимые чтения проверяют каждую
операцию. Потеря ответа не вызывает слепой повтор. Кнопка проверки делает только
чтение. При частичном результате UI показывает состояние каждой записи.

VietinBank: изучен публичный main.46c2726d00430d27ec6a.js. AutoLogout использует
meta.sessionExpiration, а API response interceptor перезапускает таймер.
SessionExtend обновляет профиль через getCustomerDetails с очисткой кеша profile;
для маршрута payment-history extends не задан. Поэтому клики ZenImport сами по
себе не продлевают сессию.

Новый MAIN-скрипт использует тот же банковский profile() и кеш. Он не копирует
сессию/токены в расширение и не передаёт профиль на backend. Привязка к экспортам
банковского webpack проверяется; при несовместимости функция прекращает работу.
Запрос — не чаще половины sessionExpiration и максимум раз в две минуты, только
на истории, в видимой сфокусированной вкладке, после активности в последние три
минуты. После ошибки запросы прекращаются до перезагрузки страницы. Нет имитации
мыши, отключения AutoLogout или автоматического входа. Состояние показывается в
нижней полосе, обезличенные события попадают в существующую диагностику.

Серверные/абсолютные ограничения банка не обходятся. На настоящей авторизованной истории 11 октября 2026 года проверено сохранение
сессии более пяти минут при работе с категориями без повторного поиска. Абсолютный
лимит сессии банка этой проверкой не определялся.
