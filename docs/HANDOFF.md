- Инициализирован Git, исходный каркас, Docker и документация сохранены отдельными коммитами. Дальнейшие этапы также коммитятся отдельно. Push и теги запрещены без отдельного явного разрешения.
- Этапы 1–2: Docker runtime и тесты, отдельная MV3 SPA, popup, подключение к backend, состояния/ошибки, защита токена от content scripts. Проверено в настоящем unpacked расширении Chromium внутри Docker; пользовательский Google Chrome вручную не проверялся.
- Этап 3: исследованы Python-клиенты, выбран самостоятельный пакет `packages/zenmoney-client` на HTTPX. Он только читает diff, сохраняет исходный текст, проверяет ответ, ограничивает размер, не выполняет автоматические повторы. OAuth onboarding не реализован; MVP принимает серверный Bearer token.
- Этап 4: миграция v2, отдельные таблицы 11 сущностей, transaction-tags, архив исходных ответов/удалений, атомарный cursor, точные суммы, страницы/фильтр истории и фактический диапазон дат в SPA. Live-полнота ещё не проверена.
- Последний полный Docker-прогон: 47 Python + 3 JS + 4 browser-теста, HTTP smoke и сохранность при пересоздании — PASS. Сервис оставлен healthy в DEMO на http://127.0.0.1:18791. Снимок v2 после обновления: data/backups/v2-20261005.sqlite3.

## Что нужно для продолжения по согласованному порядку

1. Реальный ZenMoney-токен пользователь размещает в серверном `.env`, не в чате и не в расширении. Для read-only запуска переключить ZENMONEY_MODE=live и пересоздать backend. LIVE имеет отдельный Docker volume, записи confirm/send заблокированы. Проверить реальную схему, первую загрузку, инкремент и известные операции; подтвердить желаемый период истории. Не считать min/max доказательством полноты.
2. Названия трёх банков, точные домены, первый банк и обезличенные образцы исторических операций, пагинации и форматов. Vietcombank был только примером. Реальные банковские адаптеры отсутствуют; demo не выдавать за банк.
3. После этапа 4 — этап 5: сессии импорта банковской истории, сохранение исходных/нормализованных данных, контроль покрытия, повторы частей и неоднозначные reference. Полный HTML не передавать; debug только явно и локально.
4. Этап 6: индексированный matching по точным проекциям, исторические связи и объяснимые категории по получателю и другим признакам. Текущий demo-matching по сумме/дате не закрывает категоризацию.
5. Этап 7: только после предыдущих этапов разрешить и проверить запись конкретных подтверждённых операций в ZenMoney, сохранив UUID/outbox и сверку при потерянном ответе.

## Ограничения и правила

Один пользователь/worker, SQLite WAL, сеть пока внутри транзакции. Ответ ограничен 64 МиБ; архив растёт без retention. Budget deletion по составному ключу пока явно отклоняется до реального fixture. Неизвестные поля/коллекции архивируются, но не все имеют отдельные колонки. Прототип `zen_entities` пока нужен demo-matching/outbox.

Общаться по-русски. Локальные проверки — Docker. Токены/БД/debug не коммитить, не выводить в чат, не включать в образ. Не удалять обычные тома ради теста. `.venv` только вспомогательная. Документация библиотек — Context7, затем официальные источники. Не перепрыгивать к live-записи и не объявлять fixture-тесты приёмкой реального банка/API.
