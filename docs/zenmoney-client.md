# Контракт ZenMoney в backend

Текущий SDK: `zenmoney-api-client` 0.6.0, namespace `zenmoney_api`.
Решение о разделении проектов: [zenmoney-library.md](zenmoney-library.md).
Официальный публичный протокол:
[ZenMoney API](https://github.com/zenmoney/ZenPlugins/wiki/ZenMoney-API).
Это API синхронизации через `POST /v8/diff/`, не отдельные REST CRUD endpoints.

## Чтение

Первая синхронизация использует cursor=0 и forceFetch документированных коллекций.
Далее используется последний атомарно сохранённый serverTimestamp. Country
сохраняется при наличии, но не запрашивается через forceFetch. Budget имеет
составной ключ user/date/tag, включая null category.

SDK возвращает полный словарь и неизменённый Diff.raw_json. Backend сохраняет
исходный ответ, все известные сущности/связи и неизвестные поля. Decimal остаётся
точным и при чтении, и в SQL-проекциях, и в JSON текущей сущности. Курсор обновляется
в той же SQL-транзакции, что архив, сущности, категории и удаления. Ошибка любого
объекта откатывает весь diff. См. [хранилище](zenmoney-storage.md).

Перед отправкой принудительно обновляются нужные коллекции. Полученная полная
коллекция заменяет её текущее состояние: отсутствующие записи удаляются из зеркала.
Обычный инкремент не удаляет записи по отсутствию; для него применяются deletion
и явные deleted. Не полученная коллекция не очищается.

## Запись

Готовый объект income/expense формируется builder библиотеки и сохраняется в
creation_jobs до отправки. API обновления категорий берёт свежий полный объект,
применяет transactions.update и сохраняет before/payload. Вызов upsert происходит
только после подтверждения пользователем актуального preview. Проверка после
записи использует независимое forceFetch-чтение. Системные переводы/долги не
меняются маршрутом редактирования категории.

UUID, payload и неопределённый результат переживают перезапуск. Повторная сверка
не отправляет запись. Явная подготовка повтора проверяет отсутствие прежнего UUID
в полном ответе и сохраняет этот UUID. Лимит UI-пакета в 20 относится к приложению;
SDK не устанавливает такого скрытого лимита.

В LIVE работают существующие подтверждаемые маршруты создания и категорий;
старый demo outbox остаётся доступным только в DEMO. SDK поддерживает долги,
возвраты и валютные переводы, а БД сохраняет их стороны/валюты/контрагентов.
Выбор этих типов в интерфейсе банковских операций — следующий отдельный этап.

## Авторизация, ресурсы и ошибки

ZENMONEY_TOKEN находится только в окружении backend. Расширение получает локальный
API_TOKEN; секрет ZenMoney в браузер не отдаётся. После замены .env пересоздайте
backend. OAuth — необязательная возможность самостоятельного SDK, регистрации
приложения для текущего сценария нет.

Один Client закрывается через lifespan; HTTP-соединения используются повторно.
SDK не делает автоматических повторов записи, не следует redirects и не использует
системные proxy-переменные. HTTPError, TransportError, ResponseError различаются;
токен/тело ответа не включаются в сообщение ошибки. Лимит ответа — 64 MiB, сетевой
таймаут SDK — 60 секунд. Недопустимый JSON, NaN, повторные ключи, неверная кодировка
или обратный cursor не превращаются в частично сохранённую историю.

[Проверки миграции](sdk-migration.md); автономные тесты SDK и живая тестовая матрица
находятся в самостоятельном проекте ZenMoneyAPI.
