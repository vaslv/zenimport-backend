# Клиент ZenMoney: решение и контракт

Проверено 5 октября 2026. Выбран локальный пакет `packages/zenmoney-client` (`zenimport-zenmoney` 0.1.0) на HTTPX 0.28.1. Независим от FastAPI, SQLite и расширения; публикация не нужна. Docker устанавливает пакет из исходников. Его интерфейс сейчас намеренно ограничен чтением.

## Сравнение по опубликованному коду

| Кандидат | Наблюдения | Решение |
|---|---|---|
| [zenmoney-api 0.1.0rc1](https://pypi.org/project/zenmoney-api/) | MIT, Python ≥3.12, HTTPX/Authlib, sync/async, OAuth. Предварительный релиз. В опубликованном `DiffObject` нет forceFetch/country; строгие известные поля не покрывают эволюцию API. Ответ `get_diff` допускает raw dict. | Полезен как ориентир OAuth, но интеграция потребовала бы собственного контракта и валидации. |
| [zenmoney-py 2.0.0](https://pypi.org/project/zenmoney-py/) | MIT, Python ≥3.10, requests/Pydantic, raw_diff и typed diff, покрытие country, настраиваемый timeout. Typed-модели отбрасывают дополнительные поля, raw_diff позволяет их сохранить. | Пригодный общий клиент, но добавляет второй HTTP-стек; ограничение размера, read-only граница и lossless архив всё равно нужны отдельно. |
| [python-zenmoney](https://github.com/Felixoid/python-zenmoney) | Более ранний небольшой клиент на requests. | Не выбран вместо текущего HTTPX-стека. |

Это оценка пригодности для проекта, а не заявление о плохом качестве библиотек. Их полные тестовые наборы не запускались; опубликованные исходники первых двух wheel просмотрены. Наличие raw-методов у кандидатов учтено. Собственный пакет оставляет нам обязанность сопровождать контракт и проверять изменения API.

## Чтение и сохранение контракта

Официальный источник: [ZenMoney API](https://github.com/zenmoney/ZenPlugins/wiki/ZenMoney-API). Endpoint: `POST https://api.zenmoney.ru/v8/diff/`, Bearer token. Первое чтение: `serverTimestamp=0`, явный forceFetch документированных коллекций. Последующие чтения: последний атомарно сохранённый cursor. `currentClientTimestamp` — время клиента. Это синхронизация изменений, а не постраничный REST-список за период.

Коллекции: instrument, company, user, account, tag, merchant, budget, reminder, reminderMarker, transaction; deletion — события удаления. Country встречается в ответах, но не указан как forceFetch в основной документации, поэтому принимается без запроса forceFetch=country. Расхождения с документацией зафиксированы также в [issue 757](https://github.com/zenmoney/ZenPlugins/issues/757); наблюдение в issue не заменяет проверку реального аккаунта.

Budget не имеет обычного id: ключ `(user, date, tag)`, включая null tag. Все неизвестные поля и коллекции сохраняются в исходном JSON. Клиент не округляет и не переименовывает исходный текст ответа. Структурная валидация проверяет envelope, коллекции и идентификаторы, не требует исторически меняющихся необязательных полей. JSON с повторными ключами, NaN, ошибочной кодировкой и неверным cursor отвергается.

Ошибки HTTP, транспорта и протокола различаются; текст ответа и токен не попадают в сообщение исключения. Redirect запрещён, endpoint фиксирован, системные proxy-переменные не используются. Автоповторов нет. Размер распакованного ответа ограничен 64 МиБ, timeout 60 секунд на сетевую фазу. При превышении лимита cursor не меняется: это явная ошибка, а не усечённая история. Лимит можно задать в конструкторе пакета после оценки данных; нужен запас RAM сверх размера JSON.

## Авторизация MVP

Сейчас сервер принимает уже выданный Bearer `ZENMONEY_TOKEN` через окружение. В расширении хранится только локальный `API_TOKEN`. Токен ZenMoney в браузер не отдаётся. При 401 синхронизация прекращается, старые данные сохраняются; автоматического обновления токена пока нет. Заменить токен в локальном `.env` и пересоздать backend, не передавать секрет в чат или Git.

Полный OAuth onboarding требует регистрации приложения, client_id/client_secret и согласованного redirect URI. Следующий шаг авторизации: authorization-code flow с state, обмен code только на сервере, refresh при наличии выданного refresh_token, атомарная замена секретов в серверном хранилище. Наличие, срок и механизм refresh надо подтвердить на регистрации конкретного приложения. Password grant не реализуется. До получения регистрационных данных не изображать готовую кнопку OAuth.

Live-запись запрещена двумя границами: HTTP API backend возвращает 403 на confirm/send; адаптер live не принимает коллекции для изменения, пакет вообще не предоставляет метода записи. Работа с Demo остаётся автономным тестовым сценарием.

## Проверки и пределы

Docker запускает контрактные проверки через HTTPX MockTransport: точный запрос, первая синхронизация, неизвестные поля, budget/country, 301/401/403/429/500/503, timeout/connect error без повтора, повреждённый JSON, лимит и откат cursor. Проверки backend дополнительно охватывают инкременты и удаления. Это воспроизводимые тесты контракта; живой токен ещё не предоставлен, чтение пользовательского аккаунта и фактическая глубина истории не проверены.

### Полный объект при создании (исправление HTTP 400, 13 октября 2026)

Сокращённый локальный creation payload дополняется в транспортном слое пустыми полями
`merchant`, `originalPayee`, `reminderMarker`, `opIncome`, `opIncomeInstrument`, `opOutcome`,
`opOutcomeInstrument`, `latitude`, `longitude`, `qrCode`, `source`, `incomeBankID`,
`outcomeBankID` и `viewed: true`. Исходный draft не мутируется; UUID, суммы, счета, дата,
категории и описание сохраняются. Исправление применяется и к ранее подготовленным записям.
Проверка результата допускает дополнительные серверные поля, проверяя все авторские значения.

Полнота запроса подтверждена также реализацией стороннего клиента:
https://github.com/roher-roher/zenmoney-mcp/blob/main/src/index.ts (create_transaction).
