# ZenImport

Личная интеграция вьетнамских банков с ZenMoney: backend и Chrome Extension Manifest V3 с отдельной SPA. Рабочая папка: `/Users/vaslv/Projects/Vaslv/ZenImport`.

**Docker и интерфейс расширения проверены.** Доступны импорт VietinBank, сведение истории, обновление категорий и подготовка новых операций с отдельным подтверждением создания. Создание проверено на mock API; первая реальная отправка новых записей выполняется пользователем через просмотр.

## Порядок разработки

1. Docker-запуск и тесты.
2. Интерфейс расширения Chrome, работающий с локальным backend.
3. Клиент API ZenMoney: качественная библиотека либо отдельный пакет.
4. Структура БД и загрузка доступных данных/длительной истории ZenMoney.
5. История банков и отдельные банковские таблицы.
6. Сопоставление и подсказки категорий по истории.
7. Только после предыдущих этапов — запись новых подтверждённых операций в ZenMoney.

Существующие matching/outbox — демонстрационный прототип для проверки инфраструктуры, не готовая живая интеграция.

## Быстрый запуск в Docker

Нужны работающий Docker Engine (например, OrbStack или Docker Desktop) и Docker Compose. Проверено с Engine 29.4.0 / Compose 5.1.2 на ARM64. Для тестовой конфигурации нужна поддержка Compose `!override`. Python и Node на хосте не нужны.

```sh
cd /Users/vaslv/Projects/Vaslv/ZenImport
# Только при первом запуске, если .env отсутствует:
docker compose run --build --rm --user "$(id -u):$(id -g)" init
# Обычный запуск и последующая пересборка:
docker compose up --build -d --wait backend
```

Первая команда создаёт `.env` из единого `.env.example`: все настройки перечислены явно, включая пустой `ZENMONEY_TOKEN`. API_TOKEN генерируется случайно; по умолчанию DEMO и порт 18791. DATABASE_PATH и PORT относятся только к запуску без Docker и снабжены пояснениями. Токен не выводится в логи. Существующий `.env` не перезаписывается: если файл уже есть, проверьте настройки и пропустите инициализацию.

После запуска:

- API: `http://127.0.0.1:18791`
- Health: `http://127.0.0.1:18791/health`
- OpenAPI: `http://127.0.0.1:18791/docs`
- Демобанк: `http://127.0.0.1:18791/demo-bank`

`.env.example` описывает переменные. Для другого порта измените `HTTP_PORT` в `.env` и пересоздайте backend той же командой `up`. В Docker приложение всегда слушает порт 8000 внутри контейнера; HTTP_PORT задаёт только порт на компьютере. Публикация ограничена `127.0.0.1`.

```sh
docker compose ps
docker compose logs --tail=100 backend
docker compose stop backend
# Удалить контейнер и сеть, сохранив данные:
docker compose down
```

Не добавляйте `--volumes` к обычному `down`, если данные нужно сохранить.

## Где находятся данные и секреты

Приложение работает с UID/GID 10001, файловая система образа доступна только для чтения. Временные файлы находятся в `/tmp`, БД — в `/data/zenimport.sqlite3` на постоянном Docker volume. Один worker сохраняет существующую модель конкурентного доступа SQLite.

Обычный DEMO-том называется `zenimport-demo-data`. Имя зависит от Compose project name и `ZENMONEY_MODE`; LIVE использует отдельный том. Старые файлы `data/*.sqlite3` на хосте автоматически не переносятся. Существующие банковские данные этим запуском не импортируются.

API_TOKEN передаётся через окружение только при запуске контейнера. `.env`, виртуальное окружение, БД и debug-файлы исключены из build context. Dockerfile копирует только нужные приложению каталоги; тесты и Node находятся в отдельных targets, не в runtime-образе. Базовые Python/Node-образы закреплены по digest, Python-зависимости — по версиям. При обновлении зависимостей обновляйте оба lock-файла и повторяйте контейнерные тесты.

Текущая конфигурация по умолчанию DEMO. Автоматические тесты используют отдельную DEMO-базу и mock API. LIVE включается только для личной базы с токеном ZenMoney.

## Контейнерные тесты

```sh
./scripts/test-docker.sh
```

Сценарий создаёт отдельный Compose-проект с уникальным именем, случайным внешним портом, фиксированным тестовым токеном и одноразовым томом. Секрет ZenMoney не передаётся; режим принудительно DEMO.

Проверки:

1. Серверные, миграционные и контрактные тесты и HTTP smoke внутри Python-контейнера.
2. 3 теста парсера в Node-контейнере.
3. Отдельный тестовый клиент обращается по HTTP к реальному Compose backend, импортирует демонстрационную операцию и сохраняет её в очереди.
4. Backend пересоздаётся с тем же volume.
5. Клиент проверяет сохранность операции, привязки, UUID и очереди, повторяет импорт, отправку в mock ZenMoney и проверяет отсутствие дублей.

6. Настоящее MV3-расширение проходит 4 браузерных теста: сквозной сценарий, ошибки соединения и изоляция токена от content scripts. Скриншоты — `test-results/`.

Контейнеры, сеть, образы этого одноразового проекта и тестовый volume удаляются после выполнения. Обычный `zenimport-demo-data` не затрагивается. Существующий warning TestClient о будущей миграции с httpx не влияет на результат тестов.

Подробности фактического прогона и ограничения: [приёмка](docs/acceptance.md). MV3 проверено в Chromium внутри Docker, включая desktop/mobile; ручная проверка пользовательского Google Chrome отдельно.

## Подключить расширение к локальному backend

1. В Chrome откройте `chrome://extensions`, включите режим разработчика, выберите «Загрузить распакованное расширение» и папку `extension` этого проекта.
2. Через иконку ZenImport откройте отдельный интерфейс.
3. Укажите `http://127.0.0.1:18791` и API_TOKEN из локального `.env`. Токен ZenMoney в расширение не вводится.
4. Проверьте подключение кнопкой «Обновить». Для демонстрационных данных используйте «Синхронизировать ZenMoney».

Демонстрационный сценарий: открыть `/demo-bank`, нажать иконку → «Считать операции» → «Отправить на сервер»; в SPA обновить данные, связать demo-счёт со счётом «Демо · VND», подтвердить и отправить операцию. Всё происходит в DEMO; записи в живой ZenMoney нет. Эти DEMO endpoints закрыты в LIVE; для реальной записи используются отдельные маршруты категорий и новых операций.

Полный HTML не передаётся. Debug-кнопка скачивает локальный JSON с исходными полями после явного подтверждения. Первый адаптер — VietinBank iPay, английская страница Current account / Transaction history, VND. Версия 0.2.0 запускает автоматическую загрузку месяца или шести месяцев: открывает историю, выбирает интервалы до 30 дней, собирает страницы JSON и сохраняет их с дедупликацией. Меню можно закрыть; банковскую вкладку оставьте открытой. Прогресс, отмена и скачивание журнала доступны в меню. После обновления файлов нажмите «Обновить» у ZenImport в `chrome://extensions`, проверьте версию 0.2.0, войдите в банк и нажмите «Получить историю». Chrome запросит доступ к банковскому сайту. Первоначально откройте историю нужного счёта, если в базе несколько счетов VietinBank. Подробности: [автоматическая загрузка](docs/vietinbank-automation.md); [ручная диагностика](docs/vietinbank.md). Совместимость автоматизации с живой страницей ещё требует приёмки; Docker-тесты используют синтетический банк.

## API существующего каркаса

Все `/api/*` требуют `Authorization: Bearer <API_TOKEN>`. Точные модели — в `/docs`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | Проверка процесса и режима |
| GET | `/api/state` | Данные и состояния для SPA |
| POST | `/api/imports` | Импорт исходных полей и нормализованных операций |
| GET | `/api/zenmoney/history` | Страницы истории, период и фильтр счёта |
| POST | `/api/zenmoney/sync` | Read-only diff через отдельный пакет |
| PUT | `/api/accounts/{id}/mapping` | Привязка банковского счёта |
| POST | `/api/review/{id}/confirm` | create/link/ignore |
| POST | `/api/outbox/send` | Демонстрационный прототип устойчивой отправки |
| POST | `/api/outbox/{id}/reopen` | Возврат ещё не отправлявшегося queued на review |

Банковские деньги — целые минимальные единицы (VND — đồng, USD/EUR — цент), расход отрицательный. Суммы ZenMoney проецируются в точные десятичные строки. Даты — календарные ISO без сдвига UTC. История хранится в структурированных таблицах с отдельным архивом исходных ответов; схема v2 мигрируется автоматически.

## Серверный запуск в дальнейшем

Тот же runtime-образ предназначен для запуска на сервере с постоянным томом и HTTPS reverse proxy. Сейчас опубликованный порт привязан к localhost, что подходит для reverse proxy на хосте; при отдельном proxy-контейнере потребуется общая Docker-сеть. Настройка домена, резервных копий, окончательного хранилища и LIVE-конфигурации выполняется отдельным этапом. Образ не публиковался, развёртывание на удалённый сервер не выполнялось. Проверка здесь выполнена для ARM64; архитектуру сервера нужно проверить отдельно.

## Локальная работа — уточнение 6 октября 2026

Деплой на сервер отложен до готовности функциональности. Git ведётся локально. Реальный read-only доступ ZenMoney проверен: первая и повторная синхронизации, сохранение истории и целостность SQLite. Полнота относительно приложения ZenMoney ещё требует сверки. Для LIVE заполнить существующую строку ZENMONEY_TOKEN в `.env`, установить ZENMONEY_MODE=live и пересоздать backend; Docker выбирает отдельный LIVE-том. API_TOKEN не заменять.

## Просмотр ZenMoney

Раздел содержит вкладки **Счета / Операции / Категории**. Архивные счета скрыты; включить их можно переключателем на вкладке счетов. Карточка счёта открывает его операции, сбрасывая период и страницу. В истории можно выбрать другой счёт или вернуться ко всем счетам; скрытие архивных карточек не удаляет архивные операции из общей истории.

Операции сгруппированы по датам в пределах страницы. Показаны суммы с валютами, получатель, комментарий, категории и счета; переводы между счетами не изображаются как обычный расход. В отфильтрованной истории перевода выделено движение по выбранному счёту, обе стороны доступны в подробностях.

После обновления исходников нажмите перезагрузку ZenImport на `chrome://extensions`, затем обновите открытую вкладку интерфейса расширения. Сохранённые настройки подключения остаются на месте.

## Единый список и сверка, 0.3.0

После обновления расширения откройте «Операции»: список банковских операций сгруппирован по дням, доступны фильтры счёта, периода, поиска и статуса. Раскройте строку, проверьте кандидатов ZenMoney и подтвердите «Это та же операция». Связь сохраняется локально и может быть отменена. Кандидаты сами по себе не считаются синхронизированными.

Для новых операций показаны подсказки категории при наличии как минимум двух более ранних согласованных примеров; противоречия видны отдельно. Новые записи подготавливаются в разделе «Банки» и создаются через отдельный просмотр и подтверждение. Подробности и ограничения — [docs/reconciliation.md](docs/reconciliation.md). Интерфейс ZenMoney сохраняет отдельный просмотр записей, которых нет в банковском импорте.

Для первичной загрузки истории в версии 0.3.2 доступна кнопка **«Сопоставить все
однозначные дни»** в разделе «Операции». Выберите счёт и период, проверьте число
дней/операций и нажмите кнопку один раз. Дни с любыми неоднозначными оставшимися
парами целиком остаются для ручной проверки. Поиск, фильтр статуса и пагинация
списка не ограничивают массовое действие; его область подписана рядом с кнопкой.

### Отправка выбранных категорий (0.7.0)

В LIVE доступна отдельная кнопка «Отправить категории в ZenMoney». Перед отправкой
появляется список точных изменений существующих записей. Суммы, даты и счета не меняются;
создание новых операций выполняется отдельной кнопкой и отдельным API. Сервер перечитывает актуальные данные перед записью
и проверяет результат отдельным чтением после неё. При неопределённом результате используйте
«Проверить результат отправки»: это действие ничего не записывает повторно.

«Игнорировать» в карточке банковской операции исключает её из сведения, сохраняя историю.
Отменить исключение можно через «Вернуть в проверку». Подробнее — [механизм сведения](docs/reconciliation.md).


### Новые записи в ZenMoney (0.9.1)

1. Получите данные из ZenMoney и импортируйте банк.
2. Откройте «Банки» → нужный банк, выберите счёт и период.
3. Для известных получателей с не менее чем тремя подтверждёнными операциями и одной категорией
   категория сохраняется автоматически. Если банк не передал счёт получателя, используется точное
   описание платежа с теми же условиями. Для остальных выберите и сохраните её в карточке.
4. «Создать локальные записи» сохраняет записи с назначенными категориями в нашей базе.
   Операции без категории и с возможными совпадениями пропускаются. Сеть не используется.
   До отправки локальное создание можно отменить в карточке, чтобы исправить категорию.
5. «Отправить новые записи в ZenMoney» открывает модальное окно с подготовленными записями.
   Проверьте список и подтвердите отправку до 20 записей за пакет. Обновление категорий
   уже существующих записей остаётся отдельным действием.
6. При неопределённом результате используйте «Проверить создание». Это только чтение;
   повторное создание для уже отправлявшейся банковской операции заблокировано.

Маршруты: POST `/api/new-operations/prepare`, PUT `/api/new-operations/{id}/category`,
POST `/api/new-operations/create`, POST `/api/new-operations/{id}/reopen`,
POST `/api/new-operations/preview`, POST `/api/new-operations/send`, POST `/api/new-operations/verify`.
Схема БД 10, клиент 0.3.0. Суммы/даты/счета берутся из банковского импорта и явных привязок.
Новые операции никогда не получают «Корректировку» просто из-за отсутствия истории.


### Правила категорий по имени получателя (0.10.0)

В карточке новой банковской операции выберите категорию и отметьте
«Всегда использовать выбранную категорию для …», затем нажмите «Сохранить категорию».
Правило применяется сразу, без трёх исторических примеров, к новым операциям с тем же
нормализованным именем получателя в рамках банка и направления (расход/поступление).
Номера счетов получателя могут отличаться. Ручные категории и уже созданные локальные
записи не меняются. Карточка показывает правило и позволяет удалить его; тогда
несохранённые как ручные категории снова определяются по истории. Создание локальных
записей и отправка в ZenMoney остаются отдельными действиями.
